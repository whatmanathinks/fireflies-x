What it does

Every capability below is live — not stubbed, not faked.

  • Three capture paths. A real notetaker bot dials into a call; or record the browser tab plus your mic; or upload an existing file.
  • Diarized transcripts with word-level timings, so every sentence is clickable and seeks the player to that moment.
  • AI notes — overview, chapters, action items with owners and due dates, plus per-sentence labels powering filters for tasks, questions, metrics, pricing and dates.
  • AskFred, per-meeting and workspace-wide, streaming, citing timestamps you can click.
  • Conversation analytics — talk time, words per minute, filler words, longest monologue, sentiment. Computed from word timings in TypeScript, not estimated by a model.
  • The rest of the product — channels, full-text search, tasks, soundbites, comments, bookmarks, public share links, exports, settings.

How it works

Three services, one pipeline. Each stage hands the next a plain artifact — a URL, then sentences, then notes — so any one of them can be swapped without touching the others.

01
Recall.ai
A bot joins the meeting as a participant, waits for admission, records, and returns an MP3.
02
Deepgram Nova-3
Audio becomes a diarized transcript with per-word timestamps and speaker turns.
03
GPT-OSS 120B
The transcript becomes notes, chapters, tasks and answers. Any OpenAI-compatible model works.

Decisions worth explaining

Four constraints shaped the architecture more than anything else.

Live transcription with no WebSocket server

Serverless functions can't hold a socket open. Rather than run separate infrastructure, the server mints a short-lived Deepgram token and the browser connects to Deepgram directly. Audio is never proxied, our API key never reaches the client, and no long-lived process exists.

Long-running work with no queue service

Transcribing an hour of audio outlives a request. Instead of adding Redis or Inngest, jobs live in a table keyed uniquely on (meeting_id, step), drained in-process and backstopped by a cron sweeper. Webhook retries, cron overlap and manual re-runs are all idempotent.

Map-reduce for summaries, retrieval for questions

These need opposite treatments. Summarization must read everything, so long transcripts are chunked, summarized in sections, and merged. A question only needs the relevant parts, so AskFred ranks sentences with Postgres full-text search, expands each hit into a window of surrounding context, and adds evenly-spaced samples so vague questions still get whole-meeting coverage.

Analytics in code, not in the model

Talk time, words per minute, filler words and monologue length are arithmetic over word timings. Computing them in TypeScript is cheaper, instant, and exactly right where a model would approximate.

Edge cases tested

Each of these came from actually running the thing, not from imagining what might break. All are fixed.

Stress test · 55-minute analyst call

1,032 sentences failed to summarize

Not the context window — gpt-oss-120b holds 131k tokens. The wall was Groq's free tier: 8,000 tokens per minute, counting max_tokens against the same budget. Measuring the prompt showed the per-sentence [index] (mm:ss) Speaker: prefix cost 6,443 tokens — 37% of it — and 951 of the 1,032 prefixes were redundant because the speaker hadn't changed. Fixed by grouping sentences into speaker turns (81 prefixes instead of 1,032) and map-reducing what still didn't fit.

Bot lifecycle

A notetaker nobody let in

Recall reports done with zero recordings when the bot times out in a waiting room. That read as "media still uploading", so it polled forever. Now distinguished from the status trail, and the meeting fails with something actionable: "The notetaker was never admitted to the call."

Job scheduling

Self-rescheduling jobs ran exactly once

The bot job re-enqueues itself to poll, but the runner marked the row completed after the step returned — overwriting the re-enqueue. Completion is now conditional on the row still being running. Uploads never exposed this, because they enqueue a different step.

Empty input

Recording silence retried three times

An empty transcript is deterministic — retrying can't fix it. Added a distinct permanent-failure path so it fails once, with a human explanation instead of a vendor string.

Multi-tenant demo

Every visitor shared one workspace

On a deployed link, one visitor's recordings would have been visible to the next, and anyone could delete the samples for everyone. Each demo sign-in now provisions its own workspace cloned from a template. Verified with two browser contexts: disjoint meeting ids, deletions don't cross over, and requesting another workspace's meeting returns 404.

Data integrity

Timestamps were timezone-naive

All columns were timestamp without time zone holding UTC. The app was self-consistent, but any raw SQL using now() compared local time against UTC values — which is how a scheduling bug first disguised itself. All 23 columns converted to timestamptz.

Vendor permissions

A key that couldn't mint streaming tokens

Deepgram's grant endpoint needs Member scope; ours returned 403, so every recording opened with raw vendor JSON in an alert. Capabilities are now probed once and cached, and the recorder simply doesn't attempt streaming when it won't work — batch transcription covers it silently.

Browser behaviour

A button stuck on "Opening demo…"

Back-navigation restores the page from bfcache with React state intact. Reset on pageshow and focus, with a timeout as backstop.

Serverless limits · production only

Summarization outlived the function

A 55-minute call left a job marked running for 874 seconds — impossible, because Vercel kills functions at 300. The invocation died mid-merge and the stale reclaim would have restarted it from zero, forever. Summarization is now incremental: each section is checkpointed to the job row as it completes, and an invocation nearing its budget saves and re-queues itself, so the next one resumes rather than repeats.

Scheduling

The notetaker joined, but the UI never moved

Bot polling schedules itself a few seconds out. after() drains due work immediately, so the not-yet-due poll was skipped and the chain stopped — progress only resumed when an unrelated request happened to drain the queue. Invisible locally, where a dev worker ticks every three seconds. The runner now waits for work becoming due shortly and chains onward while any remains.

Provider limits

Three different limits wearing the same status code

Groq returns 429 for per-minute tokens, for a per-request output ceiling (“Request too large”, invisible in every response header), and for an exhausted daily quota. Treating them alike produced infinite retries on requests that could never succeed, and error messages naming the wrong cause. Each is now handled on its own terms: rotate to another model, learn the ceiling and stay under it, or stop and say the quota resets at midnight UTC.

Sizing

A request no model could answer

Classification chunks were sized by input tokens alone, but the output grows with the number of sentences — each can appear in up to seven index arrays. At 272 sentences per call the answer exceeded every model’s output ceiling, so rotating between them just rediscovered the same impossibility. Chunks are now capped by sentence count as well.

  • AskFred declining to answer: asked for a listing date never mentioned in a 55-minute call, it said so rather than inventing one.
  • Vague questions with weak search matches still answered accurately, via evenly-spaced sampling plus the meeting's own notes.

Known limitations

Things I'd fix next, and constraints a reviewer should know going in.

  • Live streaming is off on the current Deepgram key — it lacks the Member role needed to mint browser tokens. Recordings are transcribed in full when you stop; you just don't see words appear live. A correctly-scoped key enables it with no code change.
  • Demo sandboxes are per-browser. Without Google OAuth configured there's no identity to tie a visitor across devices, so a different device gets a fresh workspace. Setting AUTH_GOOGLE_ID gives real persistent accounts.
  • The free model is the weak link. gpt-oss-120b writes solid notes but is measurably less precise than Claude at citing the exact line — spot-checking AskFred, one citation landed on the right topic but the wrong sentence. Adding an Anthropic key switches provider with no code change.
  • The free tier has a daily ceiling, not just a per-minute one. Groq allows 200,000 tokens per day per model. Repeatedly re-running a 55-minute transcript exhausts it, after which every request fails until 00:00 UTC. The app now says so explicitly rather than blaming the model. An Anthropic key removes the limit and skips chunking entirely.
  • Long meetings take minutes, not seconds on a free tier, because each chunk waits out the per-minute ceiling. Progress is shown; a paid tier collapses it to one or two calls.
  • Vercel Hobby crons run daily, so production bot-progress polling should be driven by the Recall webhook endpoint rather than the sweeper.
  • Diarization yields "Speaker 1 / 2 / 3." Mapping them to real people is a manual rename that applies across the transcript — the same as real Fireflies until voice profiles are trained.
  • No calendar integration. Upcoming meetings and auto-join would need Google Calendar scopes and a sync loop.
  • Single workspace per user. No teams, roles, billing or seat management.

Running it

Two variables are required; everything else unlocks a capability and degrades cleanly without it.

git clone https://github.com/whatmanathinks/fireflies-x.git
cd fireflies-x
pnpm install
cp .env.example .env.local     # DATABASE_URL + AUTH_SECRET
pnpm db:push && pnpm db:seed
pnpm dev

Sign in with Continue as Demo User — no OAuth setup needed. The README documents every variable, the deploy path, and which parts are real versus simulated.

Notes on the process

The brief suggested under ten hours. This took roughly twenty elapsed, across two days, because the goal was a product rather than a demonstration — and most of the second half went on things only real usage surfaces. The 55-minute analyst call was the single most valuable test: it broke the summarizer four separate times, each with a different cause, and none of them were guessable from the symptom. Every fix came from reading the actual error — measuring the prompt, checking the rate-limit headers, reproducing the failing chunk against the provider directly — rather than pattern-matching on the previous failure.

Built with Claude Code. Where the brief allowed a placeholder — the meeting bot — I initially simulated it, then replaced it with Recall.ai once it was clear that buying the hard part was a few hours of work rather than the multi-week project building it from scratch would have been.
